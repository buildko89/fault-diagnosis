### B. OMP の過剰選択（診断結果が信頼できないケース）🔴

`diagnose.py` の OMP 経路は常に固定個数を選びます。

```python
omp = OrthogonalMatchingPursuit(n_nonzero_coefs=max_faults, fit_intercept=False)
```

scikit-learn の OMP は `n_nonzero_coefs` を指定すると**ちょうどその本数の非ゼロ係数**を返します。つまり `max_faults=2` を渡すと、実際の故障が 1 ノードでも **必ず 2 ノードを「故障」と報告**します。

- 全探索（exhaustive）側は `for r in range(1, max_faults+1)` と本数を 1..k まで掃き、残差最小を選ぶため過不足なく当てられます。
- このため `evaluate.py` の精度評価（`best_support == correct_nodes_set` の集合一致）は、**OMP では真の故障数 < k の条件で system的に 0% 近くまで落ちます**。CLI の `diagnose` / `evaluate` は既定で OMP を使うため、この差は表面化しやすいです。

**改善案**（いずれか）:

1. **本数掃き**: `n_nonzero_coefs` を 1..max_faults で回し、相対残差が最小（または「残差がノイズ床を下回る最小本数」）の support を採用する。
2. **残差停止**: `n_nonzero_coefs` の代わりに `tol`（残差ノルム閾値）を与え、ノイズ床に達したら停止させる。
3. 少なくとも README / docstring に「OMP はちょうど k 個を返す」仕様を明記し、evaluate の集合一致判定を「真の support ⊆ 推定 support」など緩い指標と併記する。

## 3. 重大度「中」の指摘

### C. 複数励起時の OMP ターゲットが線形性を壊している 🟠

`diagnose.py`:

```python
# 複数励起(Multiple Excitations)を扱うため、線形性を保つように単純和を代表ベクトルとして採用
if num_excitations > 1:
    b_target = np.sum(np.abs(B), axis=1)   # ← 絶対値の和
```

コメントは「線形性を保つ」と書いていますが、`Z·j = ΔV` という線形関係に対して **絶対値を取って和を取る操作は非線形**で、符号情報を捨てます。`Z_mn` 側は素のまま OMP に渡されるので、ターゲットだけ非線形変換された不整合な最小化問題になり、support の選択を誤らせる可能性があります。

**改善案**: 多測定ベクトル（MMV）に正しく対応した **Simultaneous OMP（S-OMP）** を使う。実装が重ければ、各列に OMP をかけて support を多数決/和集合する、あるいは相関スコア `‖Zᵀ·B‖_row` を行ごとに評価する貪欲法へ置き換える。少なくとも `abs` を外し符号付き和や列ごと評価にする。

---

### D. `ill_conditioned` 判定が exhaustive 限定 🟠

```python
if method == 'exhaustive' and best["condition_number"] > 1.0 / rcond:
    status = "ill_conditioned"
```

OMP 経路でも `condition_number` は計算しているのに、ステータス判定の対象外です。OMP で条件数が悪い（観測ノードが故障を分離できない）状況でも `unique` と返ってしまい、ユーザは結果の不確かさに気づけません。

**改善案**: 条件 `method == 'exhaustive'` を外し、両経路共通で条件数チェックを行う。

---

### E. `Z_mn` の密行列化でスケーラビリティの主張と乖離 🟠

READMEは「数千〜数万ノード」「省メモリ」を強調していますが、`simulate.py` で転送インピーダンス行列を**密配列**で構築・保持しています。

```python
I_acc = np.zeros((circuit.num_free_nodes, len(acc_indices)))  # 密
Z_rows = spla.spsolve(Y_nom, I_acc)                           # 密 RHS → 密解
Z_mn = Z_rows.T  # (m, num_free_nodes) 密行列
```

`Z_mn` は `m × (ノード数)` の密行列で、診断（OMP / 全探索）はこの密行列上で行われます。`Y` 構築までは確かに疎ですが、**診断段は密**なのでノード数 n に対してメモリ O(m·n)、全探索は O(ₙCₖ) で、READMEの規模主張はオーバーステートです。

**改善案**:
- README の規模表現を「Y 構築・求解は疎、ただし診断段の `Z_mn` は密（m×n）」と正確に書く。
- 大規模化を本気で狙うなら、`Z_mn` を陽に作らず OMP の相関計算を `Y⁻¹` 適用（線形ソルバ）で都度評価する遅延評価に切り替える。

## 4. 重大度「低」の指摘

- `diagnose.py` の no-op:
  ```python
  if max_faults > m:
      pass   # 警告する意図が未実装のデッドコード
  ```

## 5. 良い点（維持したいところ）

- **テスタビリティ判定が理論的に正しい**: ノード分割＋スーパーシンクへの最大流で「アクセス可能ノード＋接地への頂点独立パス ≥ k+1」を判定。Togawa-Matsumoto の条件に忠実。
- **疎行列での Y 構築**（`lil_matrix` → `csr_matrix`、`A·Yb·Aᵀ`）はクリーンで読みやすい。
- **乱数の扱いが現代的**: `np.random.default_rng(seed)` を引数で受け渡し、テストの再現性を担保。
- **Strategy パターン**（omp / exhaustive 切替）とレポート自動生成まで含めた一貫した PoC 構成。
- **物理に基づく枝アドミタンス再構築**（`reconstruct_branch_faults`）と、Bridge=full-rank / Ladder=rank-deficient の対比デモが教育的。

## 7. 対応状況（2026-06-04 実施）

最優先（🔴 高）の A・B を起点に、B の修正過程で判明した C・D も併せて対応しました。

### ✅ A. 依存パッケージ修正（完了）
`requirements.txt` を実態（numpy / scipy / scikit-learn / matplotlib / networkx / pyyaml / pytest、下限バージョン付き）に更新。これでクローン直後の `pip install -r requirements.txt` → `python prototype.py` が通ります。

### ✅ B/C. OMP の過剰選択と複数励起の線形性破壊（完了）
- `diagnose.py` の OMP 経路を **S-OMP（Simultaneous OMP）** に置き換え。複数励起を「列ごとの符号付き相関の結合スコア」で扱い、壊れていた `sum(|ΔV|)`（非線形）を撤廃（C 解消）。
- **相対残差がノイズ床（`omp_residual_tol`, 既定 1e-6）を下回った時点で探索を停止**する早期停止を導入。`n_nonzero_coefs=max_faults` の固定本数選択をやめ、過剰選択を解消（B 解消）。
- 残差計算ロジックを `_build_candidate()` に共通化し、OMP / 全探索の重複コードを排除。

### ✅ D. `ill_conditioned` 判定の両経路共通化（完了）
`method == 'exhaustive'` 限定だった条件数チェックを撤廃し、全経路共通で評価（故障なし=空 support の誤判定はガード済み）。

### ⭐ 追加対応: 既定メソッドを `auto` 化（精度の信頼性確保）
**検証中に判明した重要事実**: 対称ブリッジ回路の故障 `{1,4}`（および純アクセス可能な `{1,2}`）は、**貪欲 OMP だけでなく L1（MultiTaskLasso）でも復元できない**。内部ノード 4 の故障signatureは `{1,4}` の組み合わせでしか現れず（ステップ1相関 ≈ 5e-17）、スパース近似法の構造的限界。確実に当てられるのは全探索のみ。

そこで `diagnose_node_faults` の既定を **`method='auto'`** に変更：

- 組合せ数 $\sum_r {}_nC_r \le$ `exhaustive_max_combos`（既定 100,000）なら **厳密な全探索**を自動選択。
- 超える大規模回路でのみ高速な OMP にフォールバック。

これにより、小〜中規模では「結果を信頼できる」を保証しつつ、大規模での高速性も維持。CLI に `--method {auto,exhaustive,omp}` を追加し、README の手法比較表と注意書きも更新。

### 検証結果
- `pytest tests/` → **4 passed**（既存 2 + 新規: `auto` がブリッジ内部ノード故障を厳密復元 / OMP が単一ノード故障で過剰選択しない）。
- `python prototype.py` → 正常完了（Bridge 再構築は厳密一致を維持）。
- CLI 確認: `diagnose ... --k 2`（auto）→ `[1, 4]`（残差 1.5e-16）、`--method omp` → `[1, 2]`（近似・残差 0.18）で、auto の優位を実機確認。
